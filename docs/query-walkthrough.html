insurance_rag — query-time walkthrough

What happens between a user typing an answer and getting a ranked recommendation

A RAG system for Indian term life insurance: it ingests 7 LIC policy documents into structured JSON + a vector index, then walks a user through a short Q&A and returns 3 real, ranked, grounded recommendations — never an invented product, with a real interpolated premium estimate for each. Everything below is the second half: what happens on the backend for one query, in the order it actually happens, traced against the real code.

Always-on, before any query ever arrives

Three separate processes run continuously on one Oracle Cloud VM. A query never starts any of these — it only ever talks to them.

n8n

Public webhook / chat-trigger entry point. Deliberately a thin relay only — it forwards the request to the Python service and returns whatever comes back, never re-implements any pipeline logic itself.

service/main.py

FastAPI app, systemd service. Loads all 7 policies' Layer 1/2 JSON and the precomputed rerank table into memory once at startup — a query never re-reads a file. Also holds each chat session's in-progress answers, in memory, keyed by session_id.

Q — what is FastAPI, and why does it matter?

A Python web framework for building APIs. It's the thin layer that turns the existing query/ Python modules into HTTP endpoints (/chat, /query) — with almost no boilerplate, and it validates every incoming request's shape automatically before any pipeline code runs. The pipeline logic itself (eligibility, premium math, ranking) is plain Python either way; FastAPI is just how the outside world gets to call it over HTTP.

Qdrant

Vector database, bound to localhost only. Holds one collection of policy-document text chunks, embedded once at ingestion time — a query only ever searches it, never writes to it.

Q — why go through n8n at all? why not call the service directly?

The FastAPI service has zero built-in authentication and is deliberately firewalled to only accept traffic from the VM's own internal Docker network — not the public internet. n8n already had a public HTTPS domain with a reverse proxy set up for other automations, so reusing it as the one public entry point meant not opening a new port or building auth from scratch. It also decouples the frontend from the backend: two different frontends (an n8n chat widget, and a separate static page) both call the exact same /chat endpoint through their own n8n workflow, with zero backend changes.

Q — what is available_terms() doing? what if it didn't exist?

For this exact age/cover/concern, it calls interpolate_premium() — the real step-5 pricing function — against every candidate term, and keeps only the ones that actually return a real price. For our example it returns [10, 15, 20, 25, 30, 35, 40]; then once term=30 is picked, a second call narrows payment options to just ['regular', 'limited_ppt_10'] for that specific term — "single" or "limited over 5/15 years" get rejected immediately.

Without it, the chat would accept any answer that merely parses (e.g. term=45), and the user would answer every remaining question only to discover at step 3 — after budget, after concerns, after everything — that no policy has that data at all. Worse, before this validation existed, an empty result at the very end briefly led the narrative-generation step to hallucinate a fake product to fill the gap rather than admit there was nothing to show.

Q — if premium > budget, do you drop it completely?

Yes — a policy over budget never reaches ranking or the final narrative, full stop. But it's not silently discarded: the exclusion and its exact reason are logged and returned in the response's own excluded list. Real example: {"policy_id": "955", "reason": "estimated premium 23207.63 exceeds budget 20000"} — so the "why isn't policy X showing up" question always has a real, inspectable answer, not just a missing entry.

Q — what exactly is happening? what are the 504 rows? how is relevance calculated?

At ingestion time (once, offline, not per query): every one of this corpus's 63 real document chunks (all 7 policies combined) gets scored by Voyage's reranker against each of 8 fixed "concern" phrases — 63 × 8 = 504 precomputed (concern, chunk) scores, saved to one JSON file.

At query time, this step does zero API calls — for each candidate policy, it just takes the max score among that policy's own chunks against whichever concern(s) the user picked. One concern picked here (income_replacement), so it's a straight lookup: the highest-scoring chunk each of 876/954/875 has for that one phrase.

Q — are you just sorting? or is there something more to it?

Three keys, checked in order, never blended into one number: (1) concern_match_count descending — how many of the user's stated concerns a policy actually covers; (2) relevance tier — any two scores within 0.05 of each other count as tied, so ranking isn't jumping around on statistical noise; (3) premium ascending, only as the tiebreaker inside a tier.

Real example: all 3 tie on concern_match_count (each = 1) and land in the same tier — 0.500 / 0.5234 / 0.5039 is a spread of just 0.023, well inside the 0.05 band. So this particular query reduces almost entirely to key 3: cheapest first.

Q — what's the actual difference between grounding retrieval and narrative generation?

Step 6 is a pure search — it fetches real, verbatim sentences that already exist in the policy's own document. No AI writes anything in step 6; it's the same as a paralegal pulling relevant clauses out of a contract and handing over the actual pages.

Step 7 is the only place in the whole pipeline an LLM generates new text. Gemini reads the excerpts step 6 pulled and turns them into a plain-language pros/cons paragraph — explicitly instructed to state nothing that isn't in those excerpts. Same analogy: step 7 is the lawyer explaining those clauses to a client in plain English, not allowed to cite anything the paralegal didn't actually hand them.
