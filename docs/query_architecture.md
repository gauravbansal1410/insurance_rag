# Insurance RAG — Query pipeline

Recurring, user-facing, cost-sensitive only on the LLM steps. See `docs/schema.md` for what Layer 1, Layer 2, and Layer 3 are and how they relate.

**Status: steps 1-8 built, deployed, and verified end-to-end through the real n8n chat UI as of 2026-08-01** (steps 1-2 as deterministic Q&A with real-data validation, `service/chat_session.py`; steps 3-8 as `query/`, wrapped by `service/main.py`'s `/query` and `/chat` endpoints; `service/` running on the Oracle VM as a systemd service, `n8n/insurance_rag_chat.json` imported and working). Steps 9-10 (trace log, BYOK) still design-only, deliberately deferred to prioritize a usable end-to-end path first — see "Runtime orchestration" below for the full deployment detail.

## Session state (ephemeral, per-conversation)
Turn-based slot-filling state (age given? cover amount given? priorities given? result generated?). Not on GitHub. Clears when the conversation ends. Also the state machine that makes a future chat interface a frontend-only swap, not a backend rebuild.

## Vector database choice — stated plainly, not oversold
Qdrant, chosen for self-hosting fit and native n8n integration — not a rigorous benchmark against alternatives. Pinecone was excluded early because it has no self-hosting option at all below enterprise BYOC, which conflicts with the stated infra preference (see `docs/infra-baseline.md`). Weaviate was the closer, untested alternative — comparable feature set, would likely have worked equally well. Before scaling further: confirm actual free RAM on the specific Oracle VM shape in use (see `docs/infra-baseline.md` for current confirmed specs); at this corpus's scale (low thousands of vectors) Qdrant's own footprint is small, but it's still worth checking rather than assuming.

## Pipeline

1. Frontend collects: basic profile (age, desired cover or income, budget, smoker status) and risk priorities — asked as underlying concerns via plain multi-select, no forced ranking, no rider jargon shown to the user. **v1 built as deterministic Q&A** — fixed questions, no LLM (`service/chat_session.py`'s `QUESTIONS`/`FIELD_ORDER`), matching this project's existing bias toward determinism wherever an LLM isn't strictly needed. `concern_tags` collected via a numbered list the user replies to with one or more numbers. `sum_assured_type` is not asked in v1 — defaults to `"level"` (`docs/schema.md`). **Question order: age, sum_assured, concern_tags, term, premium_payment_option, budget** — `concern_tags` deliberately asked before `term`/`premium_payment_option` (found 2026-08-01 it must be, not just "reads naturally that way"): validating a term/option answer against real data needs the concern already known, since a term can look available by age/cover alone but only exist on a policy serving a different concern entirely. `term`/`premium_payment_option` are validated live against `premium_interpolation.py`'s `available_terms()`/`available_payment_options_for_term()` — narrowed to policies actually eligible for the answers already given (age, sum_assured, concern_tags, via `eligibility_filter.bounds_ok`) — the moment they're answered, rejecting an unsupported value with a specific, actionable message instead of a generic failure at the very end (see `docs/progress/20260801-progress.md` for the three-layer bug this fixes).
2. Turn-based session handler: takes one answer at a time, updates slot-filling state, decides the next question or whether it's ready to search. **Built** as `service/chat_session.py`'s `fill_next_field(state, message)` — deliberately the one narrow, swappable seam in this step: a future conversational frontend (Ollama/Gemini-based, extending rather than rewriting v1, per explicit user intent) replaces only this function's implementation; the session-state shape and everything downstream (steps 3-8) stay the same. Not built as a formal strategy interface/registry — that would mean guessing at a future implementation's actual shape (e.g. whether it needs full conversation history, not just current field state) before it exists. Session state itself lives in the Python service's process memory (`service/main.py`'s `_sessions` dict, keyed by whatever session_id the caller supplies) — not n8n's own memory nodes, which are built for LLM conversational history, not raw slot-filling state; keeping it in Python avoids splitting this logic across two systems. Known limitation: in-memory + single-process means state is lost on a service restart and doesn't scale past one worker — fine for this project's stated personal-use scope, not fine beyond it.
3. Deterministic eligibility filter: in-memory Python filter over Layer 2 JSON (loaded from `/extracted/` at process/session start), applied independently to base plans and compatible riders — not a Qdrant payload filter. No vector-search need exists for structured field filtering at this corpus's scale (32 policies max across all categories once fully extracted), so Layer 2 is never loaded into Qdrant; Qdrant stays scoped to Layer 3 narrative-chunk vector search (step 6) only. Fast, no LLM — this step does the actual comparison math. Checks Layer 2 Group C bounds (age/sum_assured/term). Concern-tag matching (Group A) is a hard gate here, not just a sort input: at least one Group A concern_tags overlap with the user's stated concerns is required to pass — a single OR-pass (match-at-least-1), not sequential AND-then-relax queries. A rider passing this filter is never inherited from its base plan passing — each is checked independently against the user's age/sum_assured/term and concern tags, since a compatible rider can have its own narrower eligibility bounds than its base plan.
4. Fallback, two-tier: fewer than 3 matches after step 3 →
   - **Tier 1:** relax Group C bounds only (sum assured / age / term); the concern-tag gate stays firm. Flag this explicitly in the result.
   - **Tier 2** (still fewer than 3 after Tier 1): also drop the concern-tag gate, allowing zero-overlap candidates through. Flag this explicitly and distinctly from Tier 1 (e.g. "no plans directly match your stated concerns, showing closest eligible options by age/cover/term").
   Budget is deliberately not relaxed at either tier, since it isn't evaluated until step 5.
5. Premium estimation + budget filter: for each candidate surviving steps 3–4, compute an estimated premium via deterministic Python linear interpolation (a manual two-point formula — no LLM, no numpy dependency needed at this data size) between the two nearest points in that policy's Layer 1 `sample_illustrative_premiums` (not Layer 2), against the user's actual age/sum-assured/term (not a fixed baseline). Interpolation is matched within the same `premium_payment_option` column (single / limited_ppt_5 / limited_ppt_10 / limited_ppt_15 / regular) AND the same `sum_assured_type` (`"level"` | `"increasing"` — a Layer 1 field added 2026-07-27 after finding some policies price a level-sum-assured and an increasing-sum-assured death benefit as separate tables; defaults to `"level"` when a policy offers no such choice) — never interpolated across different payment-option columns or across level/increasing tables, since neither pair shares the same curve. Candidates whose profile falls outside the policy's sample table range for that column are excluded from results, with the reason logged — the query still completes. Then filter out any candidate whose interpolated premium exceeds the user's stated budget, same exclude-and-log mechanism, not a query failure. Budget can only be filtered here, not in step 4's eligibility fallback, since it depends on the interpolated premium this step computes — it isn't a static Layer 2 Group C field. Guards against concern-matching + semantic relevance alone systematically favoring feature-rich, expensive policies.
   - **v1 pilot exception (built 2026-08-05), policy 876 + `premium_payment_option: "regular"` + `sum_assured_type: "level"` only:** `query/premium_interpolation.py`'s `interpolate_premium()` dispatches to a precomputed lookup (`query/premium_lookup.py` + `query/premium_lookup.json`, built by `query/build_premium_lookup.py` — see `docs/schema.md`'s premium-lookup artifact section) instead of the two-point linear formula above, for this exact combination only — every other policy and every other payment-option/sum_assured_type combination on 876 itself is unaffected (scope-guarded dispatch, verified directly, not just assumed). Two independently-modeled axes: (1) age x term — genuinely non-linear (real scraped data confirmed the mortality-cost curve accelerates), handled via **bilinear interpolation** over the real (age, term) points actually gathered; a query outside the known grid is excluded, never extrapolated. Validated via leave-one-out: median error 1.06%. (2) sum_assured — separable from term, and handled via a **closed-form formula parsed directly from Layer 1's `rebate_structures.high_sum_assured_rebate_table`** (corrected 2026-08-05 — an earlier version wrongly concluded this needed an empirical multiplier table; see open questions below), so this axis needs zero scraping and covers the policy's full sum_assured range, not just the SA values that happened to get scraped.
   - **Generalized 2026-08-05, policy 859's SA axis added, full entry built 2026-08-08:** the SA-scaling formula turned out not to be one universal equation — 859's real rebate table is a flat Rupee-per-mille-of-Sum-Assured deduction, not a percent-off-premium discount like 876's. `query/premium_lookup.py`'s `compute_sa_adjustment()` dispatches on the rebate table's own `type` tag (`"percent_of_tabular_premium"` vs `"per_mille_of_sum_assured_rupees"` — set by the extraction prompt itself, not inferred downstream; see `docs/schema.md`'s extraction-rule caveats for the full prompt-fix story). `query/build_premium_lookup.py` was generalized from a single 876-hardcoded script into a `POLICIES`-list-driven build (each entry its own scope: reference SA, ground-truth CSV, rebate-table navigation config) once 859 needed the same build with different values. 859's age x term grid comes from a real 52-point scrape (its brochure alone gave only 2 terms) covering its full valid (age, term) domain exhaustively at 5-year steps — cleaner than 876's scatter-then-gap-fill approach since 859's domain is a simple triangle (`entry_age` 18-65, `policy_term` 5-40, capped by `age + term <= age_at_maturity_max`). Leave-one-out validation: median error 1.66%, no thin-anchor outlier like 876's. Independently spot-checked against a real LIC quote at 5x the scraped reference SA (age 31/term 20/SA 25L): 1.3% spread against the lookup's prediction. `query/premium_interpolation.py`'s dispatch no longer hardcodes a single policy scope either — it now reads each `premium_lookup.json` entry's own stored `premium_payment_option`/`sum_assured_type` directly, so a policy/option combination missing from the table transparently falls through to the original linear interpolation with no per-policy code change needed.
   - **878 built 2026-08-11 (24-point scrape, terms 15-30 to keep its Limited/PPT=10 payment structure valid — no Regular option exists on this `credit_life` policy). 877 built the SAME day WITHOUT its own full scrape** — `build_premium_lookup.py` gained a `DERIVED_POLICIES` path that rescales an already-built sibling's `age_term_grid` by a factor calibrated against a handful of the target policy's own real anchor points, used only once shape-transfer between the two was independently confirmed first (see open questions below: 877-vs-878 matched within 0.1-2.7% at every one of 877's 6 spot-check points). 877's grid = 878's grid x 1.262 (calibrated from those 6 anchors, which ranged 1.2416-1.2766 — matching the earlier finding directly), with the 6 real points substituted back in verbatim at their own (age, term); every other point is tagged `"source": "derived_from_878"` in the built artifact, not silently presented as scraped. `sa_scaling` is still built from 877's own independently-extracted rebate table — only the age x term axis benefits from the transfer, since the SA-scaling formula was already established as policy-specific. This roughly halves the scraping effort for a same-family sibling pair going forward: one full grid plus a small spot-check on the other, rather than two full grids.
6. Narrative retrieval: Qdrant vector search over Layer 3 chunk-level records, restricted to the policy_ids that survived steps 3–5 (not an independent global search) — top ~15–20 candidates within that surviving set.
7. Reranking + sort: relevance scores come from an **offline-precomputed lookup, not a live Voyage call**, as the default path — see "Reranking data source" below for why and how. Final order uses `concern_match_count` (from step 3) as the primary sort key. Within each count-block, candidates are grouped into relevance tiers by rerank score: any two candidates whose rerank scores fall within a tolerance band of each other (placeholder threshold: 0.05 — **UNCALIBRATED**, not validated against any real rerank score distribution) are treated as tied on relevance and placed in the same tier; a rerank score gap larger than the threshold puts candidates in different tiers, and the higher-scoring tier always wins. Within a tier, candidates are sorted by interpolated premium (step 5) ascending. This is not blended into one weighted number.
   - **Decision, flagged rather than silently picked:** premium only breaks ties within a relevance tier, never overriding a real relevance gap across tiers — this is why the tolerance band exists instead of an exact-score tiebreak, which would almost never fire given rerank scores are floating point and would leave premium as dead weight in the sort. Keeps ranking explainable for the eventual LLM judge / golden-set evaluation, and avoids inventing an arbitrary weighting formula between concern match, semantic relevance, and price.

## Reranking data source: precomputed lookup, live rerank as a rare fallback only

Found 2026-07-31, running steps 6-7 end-to-end against live data for the first time: a live Voyage `rerank-2.5-lite` call per query does not meet a live query's latency bar. Step 6's documented "~15-20 chunks" is typically 15-25K words at this corpus's actual section sizes — over Voyage's free-tier 10K TPM cap in one request, needing 4-5 batches paced a mandatory 65s apart. That's a multi-minute *floor* on every query, not a contention-driven worst case (see `docs/progress/20260731-progress.md` 2026-07-31 for the full investigation).

Fix: the relevance signal in steps 6-7 depends only on the user's `concern_tags` (a fixed, closed 8-tag set — `query/concern_tags.py`, no free text), never on the user's numeric profile fields (age/sum_assured/term) — those only drive steps 3-5's eligibility filter. That decoupling means relevance can be **precomputed once, offline, independent of any specific user**:

- `chunking/precompute_rerank_scores.py` reranks every Layer 3 chunk against each of the 8 fixed tags individually (not all 255 possible tag *combinations* — reranking the full corpus against every combination would take days at free-tier pace; 8 independent tags is tractable and grows only linearly as new policies are ingested). Output: `chunking/precomputed_rerank_scores.json`, keyed `tag -> chunk_id -> {policy_id, score}`.
- `query/precomputed_relevance.py` is the live-path lookup: given the user's selected `concern_tags` and the policy_ids surviving steps 3-5, returns a per-policy score by taking the **max** precomputed score across the selected tags and that policy's chunks — a pure in-memory lookup, zero Voyage calls, no query-time latency. This is a deliberate approximation, not identical to reranking one joined query string against each chunk (which is what the live path in `narrative_retrieval.py` still does) — but it mirrors an approximation already accepted elsewhere in this design (`max_rerank_score_by_policy` already collapses per-chunk scores to per-policy via max, not an average).
- **Fallback (rare, not routine):** a policy missing from the precompute table entirely (freshly ingested, precompute not yet run for it) falls back to a live rerank for just that gap — capped to whatever fits in one Voyage request, never the multi-batch/multi-minute path, per `rerank_and_sort.py`'s existing batching logic.
- Precompute is refreshed by re-running `chunking/precompute_rerank_scores.py` (merges into the existing table by `chunk_id`, doesn't recompute the whole corpus) — normally triggered automatically by `chunking/ingest_policy.sh` (see `docs/ingestion_architecture.md`) whenever a new policy is ingested.
8. Narrative generation: Gemini flash-lite explains the top 3 candidates in plain language with pros/cons, grounded only in each candidate's step 6 narrative chunks (never inventing a feature/condition not present there), and discloses that shown premiums are reference estimates from linear interpolation, not exact quotes. **Scope note:** covers base plans only for now, not plan + rider combos as originally envisioned — steps 3-5 don't implement rider eligibility/combination yet, so there's nothing to combine with a base plan yet. The only genuinely slow step — design the loading state around it specifically. Built as `query/narrative_generation.py` + `docs/prompts/prompt_c_narrative.txt`, verified against live Gemini output: correctly grounded real facts (cover amount, payout structure, free-look period) from source chunks, never recommended one candidate over another, and reproduced the disclosure paragraph verbatim as instructed. One prompt-following gotcha found and fixed — the per-candidate context block's own heading format (`### Candidate N: ...`) was sometimes echoed back verbatim as the model's own section heading instead of the real plan name, the same failure shape as a prompt's own example value leaking into extraction output (`docs/progress/20260726-progress.md`'s trap 14 finding); fixed by removing the markdown heading syntax from the context block entirely.
9. Trace log write (async) after steps 3–8.
10. BYOK check: client-supplied Gemini key used if present, falls back to your stored n8n credential otherwise. **Not built yet** — `narrative_generation.generate_narrative()` already accepts an `api_key` override param (built for exactly this), but neither `service/main.py`'s request models nor the n8n workflow plumb a user-supplied key through to it yet.

## Runtime data source for steps 3–5

The live query pipeline (n8n, Oracle VM) reads Layer 1/2 JSON for steps 3–5 from a local git clone of this repo on the VM, kept current via `git pull` — a manual, end-of-session step for now, not automated (see `docs/infra-baseline.md`'s end-of-session checklist). Uses the same scoped fine-grained PAT and local (non-global) git identity already established for this repo's clone-safe exception in `docs/infra-baseline.md`. The live query path must never fetch from GitHub's raw endpoint per query — that pattern belongs to ingestion/admin-time tooling only, not a request-serving path.

## Runtime orchestration: n8n as a thin layer, not a re-implementation

Decided 2026-07-31, after steps 3-8 were already built and verified as plain Python (`query/`): n8n does **not** reimplement any of steps 3-8's logic as native nodes (Code nodes, per-step HTTP Request nodes to Qdrant/Voyage/Gemini, IF-node branching). That logic already represents real, tested effort — including bugs only found by actually running it (the Voyage batching/retry fix, the rerank tier-assignment logic, the narrative-generation heading-echo fix) — and n8n's Code-node environment is a much thinner, harder-to-debug place to redo that same work a second time, with real risk of silently reintroducing bugs already fixed once.

Instead: **n8n handles only what it's actually suited for** — the webhook/chat trigger and (eventually) the BYOK key check (step 10, not built yet) — and calls out to a small, self-hosted Python service (FastAPI, `service/`) on the same Oracle VM that directly imports and runs the already-built `query/` modules. Turn-based session state (steps 1-2) ended up living in the **Python service**, not n8n itself, once v1's deterministic-Q&A design was settled — n8n's memory nodes are built for LLM conversational history, not raw slot-filling state, and keeping it in Python avoids splitting this logic across two systems (see step 2 above).

**Resolved:** one endpoint per pipeline step vs. a single "run query" endpoint — went with a single endpoint, in fact two: `POST /query` (steps 3-8 only, for direct calls) and `POST /chat` (steps 1-8: slot-filling, then `/query`'s logic once complete, for n8n's Chat Trigger to call as a single, near-stateless relay). n8n's actual job is now close to just: **Chat Trigger → HTTP Request (`POST /chat`) → Respond with whatever `reply` comes back** — no per-step nodes, no node-side branching.
