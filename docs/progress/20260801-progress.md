## Decided: keep precompute at 8 individual tags, not all 255 tag combinations

Raised by the user once the VM removed the "have to babysit it"
constraint: since it can now run unattended indefinitely, why not
precompute every possible `concern_tags` combination instead of the
8 tags individually, for an exact (not approximated) live-path lookup?

Recommended against it, for reasons that don't go away just because the
job runs silently:
- **Token budget, not wall-clock time, is the real constraint.**
  Reranking cost scales with documents x queries; 255 combinations
  against the same 63 chunks is ~255x one tag's cost - at this
  category's size alone, roughly ~25M tokens (~12.5% of Voyage's entire
  200M/month free allowance) for one precompute pass. At the full
  32-policy corpus this project is scoped to, a full-combination
  precompute would consume a large fraction of the *entire monthly*
  free budget, repeatedly, every time the tag vocabulary changes
  (`docs/schema.md`'s own checklist already anticipates that as a real,
  expected event, not hypothetical).
- **Doesn't scale as the tag set grows** - 8 tags -> 255 combos, 9 tags
  -> 511 combos, doubling with every new tag vs. the per-tag approach's
  linear growth. This was the actual original reason 8-tags-not-combos
  was chosen; moving to a non-sleeping VM doesn't change this math.
- **Not clearly even a quality improvement** - real data already shows
  rerank scores clustering very tightly for similar policies (one
  earlier test: 4 candidates within a 0.0078 spread), which the
  tolerance-band tiering already absorbs; there's also a real argument
  that blending unrelated concerns into one query *dilutes* signal for
  each individually, making max-over-tags not just cheaper but possibly
  more interpretable, not merely an inferior approximation.

Decision: staying at 8 tags. If more confidence in the approximation is
wanted later, a cheap spot-check of a handful of real combinations
against the max-over-tags result costs far less budget than doing all
255 for real.

## Bug found and fixed: `plan_name` fallback didn't handle a `None` value, only a missing key

The real end-to-end test's narrative headings showed raw `policy_id`
values (`### 512N351V02`, `### 876`) instead of real plan names.

"plan_name", candidate["policy_id"])` only falls back when the KEY is
absent - `plan_name` is present but **`None`** for all 7 term-assurance
Layer 1 records (checked directly, not assumed from one or two
samples), so `.get()` returned the literal `None`, meaning the prompt
sent to Gemini literally contained "Plan name: None". Earlier test runs
that showed correct plan names ("LIC's Yuva Term" etc.) only worked by
coincidence - Gemini occasionally pulled the real name from the
grounding document excerpts instead of the broken structured field,
not reliably.

Fixed: `.get("plan_name") or candidate["policy_id"]` - handles both the
missing-key and the present-but-None cases. Verified fixed on a second
full `/chat` run: headings now cleanly show `policy_id` as the intended
fallback (no literal "None" leaking into the prompt) rather than
crashing or producing garbage - not pretty, since the underlying data
gap remains, but no longer buggy.

**Not fixed, flagged for a future ingestion-focused session:**
`plan_name` is `None` for **all 7** term-assurance Layer 1 records, not
an isolated case - a real, universal extraction gap, given
`docs/schema.md` documents `plan_name` as a required top-level Layer 1

this session (deliberately, to stay focused on finishing the query

## Built: n8n workflow + full service deployment to the Oracle VM

**`n8n/insurance_rag_chat.json` + `n8n/README.md`:** hand-authored
workflow JSON (n8n has no API key configured, so built for manual
import rather than via n8n's REST API) - three nodes: **Chat Trigger**
(static greeting asking for age - n8n's chat UI can't speak first
through the workflow itself, so the first real message is always the
user's actual answer) -> **HTTP Request** (`POST /chat`, forwarding
`sessionId`/`chatInput` as `session_id`/`message`) -> **Set** (maps
`reply` to `output`, what n8n's plain chat workflow needs to display).
Matches `docs/query_architecture.md`'s "Runtime orchestration" design:
n8n stays thin, no reimplemented step 3-8 logic.

**Deployed `service/` to the Oracle VM as a systemd *user* service**
(`~/.config/systemd/user/insurance-rag-service.service`, `enable --now`
so it survives both logout via the lingering set up during the
2026-07-31 precompute incident, and a reboot, with `Restart=on-failure`).
Installed `fastapi`/`uvicorn` on the VM first (not previously needed
there). Bound to `172.17.0.1:8000` specifically - the Docker bridge
gateway IP (confirmed via `docker network inspect bridge`), not
`0.0.0.0` (would expose this zero-auth service on the VM's public
interface too) and not `127.0.0.1` (unreachable from n8n's container).

**Real blocker found and fixed, not a Docker networking guess:** n8n's
container still couldn't reach `172.17.0.1:8000` ("Host is
unreachable") despite correct bridge routing - root cause was the
host's own `iptables` `INPUT` chain, which only allows ports 22/80/443
plus established connections, rejecting everything else (including
container-to-host traffic) with `icmp-host-prohibited`. This is a
production VM that also handles SSH access, so treated as a genuinely
risky change: confirmed the persistence mechanism first
(`netfilter-persistent`, rules in `/etc/iptables/rules.v4`), got
explicit user confirmation before touching the firewall, added one
narrowly-scoped rule (`-i docker0 -p tcp --dport 8000 -j ACCEPT`,
inserted before the existing REJECT), verified a *fresh* SSH connection
still worked immediately after (not just the already-open session),
verified n8n's container could now reach the service
(`docker exec n8n wget -qO- http://172.17.0.1:8000/health`), then
persisted via `sudo netfilter-persistent save`.

## Critical bug found via real n8n testing: empty-candidate hallucination

First real chat test through the actual n8n UI (age 31, Rs 1 crore
cover, 40-year term, income replacement) returned a fluent, well-formatted
narrative describing three completely fabricated policies - "Tata AIA
Sampoorna Raksha Supreme," "ICICI Prudential iProtect Smart," "HDFC
Life Click 2 Protect Super" - none of which exist anywhere in this
LIC-only corpus. Investigated immediately rather than treated as a
curiosity, given hallucinated insurance product advice is a serious
trust failure, not a cosmetic issue.

Root cause, reproduced locally before fixing anything: 4 policies
passed eligibility (age/sum_assured/term bounds + concern match), but
**zero survived premium interpolation** - none of their
sample-premium tables had a row for a 40-year term. `top3` came out
empty, and `generate_narrative()` was still called with it - producing
a prompt with a blank candidates section, which Gemini filled by
inventing three fake products instead of refusing. Confirmed via
direct reproduction that a prompt instruction alone cannot be trusted
to refuse gracefully when handed nothing to ground on.

Fixed at two layers, both hard code guards, not prompt tweaks:
- `run_query_pipeline.py`: checks for an empty `top3` and returns an
  honest "no eligible plans found" message, never calling Gemini.
- `narrative_generation.generate_narrative()`: raises `ValueError` on
  an empty candidate list - defense-in-depth for any future caller
  that reaches this function the same way by accident.

**User pushed back correctly on stopping there:** a generic "sorry,
nothing found" after all 6 questions is a much worse experience than
catching the problem at the exact question that caused it. Rebuilt the
fix properly instead of settling for the safety net:

- New `available_terms()`/`available_payment_options_for_term()`
  helpers in `premium_interpolation.py` query real
  `sample_illustrative_premiums` data for which terms/options actually
  have coverage.
- `chat_session.py` validates the user's `term` and
  `premium_payment_option` answers against these helpers the moment
  they're given, rejecting an unsupported value immediately with a
  specific, actionable message (e.g. "Available terms: 20, 25") instead
  of silently accepting it.
- **First version was still too shallow:** checked availability across
  the *whole corpus*, not the policies actually eligible for this
  user's age/sum_assured. Found via a second real test (Rs 1 crore
  cover, term 25, regular payments) that this still fell through to
  "no eligible plans found," because the only policy with that exact
  premium column has a Rs 25L sum-assured cap - term 25 "existed" in
  the data, just never on a policy this user could actually buy. Fixed
  by making `eligibility_filter.py`'s `_bounds_ok` public (`bounds_ok`)
  and reusing it in the availability helpers to filter to the eligible
  subset before counting a term/option as available.
- **Still incomplete after that:** a third real test (age 31, Rs 1
  crore, term 25) showed term 25 was *still* reported available, because
  two other policies (877/878) have 25-year data and enough cover room -
  but they only serve `debt_linked_cover`, not `income_replacement`, so
  they were never real options for this user's stated concern. Fixed by
  adding concern_tags overlap to the same eligibility check
  (`_policy_matches()`), and - since concern_tags is needed *before*
  term/payment_option can be validated - reordering
  `chat_session.py`'s `FIELD_ORDER` to ask concern_tags earlier: age,
  sum_assured, concern_tags, term, premium_payment_option, budget
  (concern_tags was previously asked last).

Each of these three layers was found by a real conversation surfacing
a real dead end, not by anticipating them in advance - confirmed fixed
by testing the exact failing profile again after each fix, all the way
through to a successful, correctly-narrowed result.
