# Progress Log — 2026-07-31

## Built: query/ — step 6 (narrative retrieval)

New `query/narrative_retrieval.py`. Qdrant vector search over Layer 3
chunk-level records, filtered to only the `policy_id`s that survived
steps 3-5 (`Filter`/`FieldCondition`/`MatchAny` on `policy_id`, not an
independent global search) — Qdrant does semantic search only inside an
already-narrowed set, per `docs/query_architecture.md` step 6.

- `synthesize_query_text()`: deterministic, no-LLM synthesis of the
  user's Group A `concern_tags` (the fixed 8-tag set, no "other"
  catch-all — `docs/schema.md`) into one natural-language query string
  via a fixed tag -> phrase mapping. Keeps step 6 as fast/deterministic
  as steps 3-5, no LLM call.
- `embed_query()`: embeds that query string with `voyage-law-2` using
  `input_type="query"` — deliberately not `"document"` (which
  `embed_and_load_layer3.py` used for the chunks). Voyage's asymmetric
  embedding scheme means query and document text are embedded
  differently for retrieval; using the wrong `input_type` silently
  degrades match quality rather than erroring, so this was called out
  explicitly rather than left to be discovered later.
- `retrieve_narrative_chunks()`: embeds the query, then
  `qdrant_client.query_points()` filtered to the surviving
  `policy_ids`, `limit` ~15-20 per the doc.
- Verified against live data (tunnel + real `insurance_rag_layer3`
  collection): correct filtering (an out-of-corpus `policy_id` returns
  0 hits, confirming the filter is actually enforced, not just
  returning everything); real cosine-similarity scores clustered
  tightly (0.42 → 0.38) across all hits for 3 term-assurance policies —
  expected, since similar plans share similar language, and exactly why
  step 7's rerank + `concern_match_count` tiebreak exist rather than
  relying on raw vector similarity alone.

## Built: query/ — step 7 (reranking + sort)

New `query/rerank_and_sort.py`. Voyage `rerank-2.5-lite` re-scores step
6's retrieved chunks for semantic relevance; results are then sorted
per `docs/query_architecture.md` step 7 — not one blended score:

1. `concern_match_count` (step 3) descending, primary key.
2. Within a `concern_match_count` block, group into relevance tiers by
   rerank score, using the doc's placeholder tolerance band (0.05,
   still uncalibrated).
3. Within a tier, sort by interpolated premium (step 5) ascending.

Implementation notes:

- Rerank scores are per-chunk; `concern_match_count`/premium are
  per-policy. `max_rerank_score_by_policy()` collapses to one score per
  policy by taking the max across that policy's retrieved chunks — a
  policy's relevance is judged by its single most relevant passage, not
  penalized for having some boilerplate sections.
- `_assign_tiers()`: the doc's "candidates within a tolerance band of
  each other are tied" isn't transitive (A~B, B~C doesn't imply A~C).
  Resolved with the simplest defensible rule — sort descending, cut a
  new tier whenever the gap between *consecutive* scores exceeds the
  tolerance — rather than inventing a chaining/clustering rule the docs
  don't specify.
- `rank_candidates()` flags rather than silently drops candidates that
  survived steps 3-5 but got no chunk back from step 6's retrieval
  (`rerank_score: None`, sorted last within their `concern_match_count`
  block) — same "flag, don't silently guess" pattern used elsewhere in
  this codebase (e.g. `premium_interpolation.py`'s ambiguous-row
  exclusion).

## Bug found + fixed: Voyage rerank calls need the same batching as embeds

`rerank_chunks()` originally sent all of step 6's retrieved chunks'
full text in a single `rerank()` call. Confirmed 2026-07-31 that 20
full-section chunks (~25.8K words) is ~33.5K estimated tokens — over
3x Voyage's free-tier 10K TPM cap in one request. Retrying with backoff
can't fix a single request that's already over the limit by itself,
only a transiently-full window.

Fixed by batching the same way `embed_and_load_layer3.py` already does
(greedy word-budget batching, `MAX_BATCH_WORDS=5000`, batches paced
`SECONDS_BETWEEN_BATCHES=65` apart), with per-batch retry-with-backoff
on `RateLimitError` (`MAX_RETRIES=3`). `rerank_chunks()` now returns
plain `{"chunk_index": i, "relevance_score": ...}` dicts with indices
already remapped across batches, rather than Voyage's own
per-batch-relative `RerankingObject.results[].index`, which would only
make sense within one batch's document list.

## Reliability finding, not a bug: apparent "hangs" were rate-limit backoff, not stuck code — but the "15+ minutes" estimate itself was wrong

While verifying the batching fix, a debug script and later the real
`rerank_and_sort.py` `__main__` run both appeared to hang with 0% CPU
and no output past step 6, estimated at the time (by counting
conversation turns / scheduled-wakeup intervals, not a clock) at 9-15,
then 30+, minutes. Spent real time diagnosing this as a suspected
hang (added `REQUEST_TIMEOUT_SECONDS=30` to both `QdrantClient` and
`voyageai.Client` as a real fix regardless — neither client raised
promptly on a stalled connection without one, which is worth keeping
independent of the rest of this finding).

**Correction:** the elapsed-time estimates driving that whole
investigation were wrong, confirmed by checking `ps -o lstart,etime`
against actual wall-clock time instead of counting turns/wakeups — a
run believed to be 30+ minutes in was, per `ps etime`, only ~3.5
minutes in. Turn-counting/scheduled-wakeup-counting is not a reliable
proxy for real elapsed time and shouldn't be used to diagnose
hangs/timeouts again — always check `date`/`ps etime` directly.

With that corrected, the actual, clock-verified behavior: a live run
against the real 4-policy/20-chunk profile crashed via a legitimate,
correctly-raised `RateLimitError` after **6m34s** real time (process
`lstart` 16:57:53 -> crash at 17:04:27) — not a hang, the retry loop
worked exactly as designed (3 attempts x 65s backoff on one batch,
exhausted, correctly re-raised rather than looping forever). The
account was still under rate-limit contention from earlier ad-hoc
debug `rerank()`/`embed()` calls made during the same investigation
(which kept Voyage's rolling 60s TPM window near capacity), so 3
retries wasn't enough headroom to outlast it. Fixed by bumping
`rerank_and_sort.py`'s `MAX_RETRIES` from 3 to 6 (more wall-clock
patience, no cost) rather than by adding a timeout (that part was
already fine — the process was correctly retrying and correctly
crashing, just running out of attempts too soon).

Lesson for future debugging on this project: (1) don't make
parallel/exploratory Voyage calls while a real batched pipeline run is
also in flight — it competes for the same rate-limit window; (2) when
judging whether something is stuck, check `ps etime`/`date`, never
estimate from how many turns or scheduled wakeups have passed.

## Design concern raised: is Voyage's free tier viable for the live query path at all?

Watching real query-time latency during this verification (a floor of
several minutes per query even in the best case, once step 6 needs its
full ~15-20 chunks rather than this session's deliberately-shrunk
10-chunk test) raised a real question: `embed_and_load_layer3.py`'s
"expect minutes, not seconds" pacing was designed for one-time,
admin-triggered ingestion — that assumption does not transfer to a
live, user-facing query path, and this is the first session that
actually exercised steps 6-7 end-to-end for real to surface it. At
typical chunk sizes (~800-2200 words/section measured this session),
step 6's documented "~15-20 chunks" is commonly 15-25K words, needing
4-5 rerank batches at a mandatory 65s spacing each — a several-minute
floor on *every* query, not a contention-driven worst case. Already
flagged as an open question in `docs/query_architecture.md` ("the real
constraint on concurrent live-query throughput... worth revisiting
past solo personal use") but the severity (multi-minute baseline
latency, not a throughput ceiling under load) wasn't previously
demonstrated. Not resolved this session — options discussed: add a
Voyage payment method (lifts the RPM/TPM ceiling; free 200M
tokens/month still apply per Voyage's own error text, so may not
violate the project's $0-recurring constraint at this scale, but
unverified against Voyage's actual paid-tier limits/pricing); rerank
only one representative chunk per surviving policy instead of top-15-20
across all of them (keeps a single rerank call within one free-tier
request, no batching needed at query time); or drop step 7's rerank
call entirely for this corpus size (876/875 scored identically to 6
decimal places in this session's testing, suggesting rerank's
discriminative value here may not be worth its cost). Needs a decision
before steps 6-7 can be considered production-ready for a live query
path, independent of their logic already being verified correct.

## Built: offline-precomputed reranking, replacing a live Voyage rerank call at query time

Direct response to the Voyage-viability finding above. Since step 6-7's
relevance signal depends only on the user's `concern_tags` (a fixed,
closed 8-tag set, `query/concern_tags.py` — extracted from
`narrative_retrieval.py`, which now imports it instead of duplicating
it) and never on the user's numeric profile fields (age/sum_assured/
term, which only drive steps 3-5's eligibility filter), relevance can
be precomputed once, offline, independent of any specific user:

- `chunking/precompute_rerank_scores.py`: reranks every chunk passed in
  against each of the 8 fixed tags *individually* (not all 255 possible
  tag combinations — reranking the full corpus against every
  combination would take days at free-tier pace; 8 tags is tractable
  and grows only linearly as policies are added). Reuses
  `rerank_and_sort.py`'s batching/retry logic directly via a small
  `_ChunkAdapter` (wraps a plain chunk dict in a `.payload` attribute,
  matching Qdrant's `ScoredPoint` shape `rerank_chunks()` expects) —
  deliberately did not change `rerank_chunks()`'s already-validated
  interface. Output: `chunking/precomputed_rerank_scores.json`, keyed
  `tag -> chunk_id -> {policy_id, score}`, merged with any existing
  file by `chunk_id` (idempotent, same pattern as the Qdrant upsert).
- `query/precomputed_relevance.py`: the live-path lookup —
  `lookup_relevance_by_policy()` takes the user's `concern_tags` and
  the policy_ids surviving steps 3-5, returns a per-policy score as the
  **max** precomputed score across the selected tags and that policy's
  chunks. Zero Voyage calls, no query-time latency. Also returns which
  policy_ids aren't covered by the table at all, for a fallback to a
  live (cheap-only) rerank — not built this session, the lookup and its
  missing-policy signal are.
- **Flagged approximation, not hidden:** combining multiple selected
  tags via max-over-independently-scored-tags is not identical to
  `narrative_retrieval.py`'s live path, which joins tags into one query
  string and reranks against that. Documented as a deliberate
  approximation (in the module docstring, `docs/schema.md`, and
  `docs/query_architecture.md`) rather than presented as equivalent —
  mirrors an approximation already accepted elsewhere in this design
  (`max_rerank_score_by_policy` already collapses per-chunk scores to
  per-policy via max, not an average).

**Test run (1 policy, 875, 9 chunks × 8 tags):** launched in the
background to validate the new modules mechanically before committing
Voyage-call budget to the full 7-policy/63-chunk corpus — real-time
progress confirmed via `ps etime` this time (see the timing-methodology
correction above), not turn-counting.

## Built: chunking/ingest_policy.sh — one orchestration script for new-policy ingestion

Directly requested to prevent the 954/955 policy_id bug class from
recurring: chains Layer 1+2 extraction -> Layer 3 chunking -> embedding
-> precompute in one command, so no step can be manually forgotten or
run with a mismatched identifier. The specific fix: it takes a
`<file_id>` argument (used only to name Layer 1/2's output files,
matching `run_pipeline.sh`'s existing convention) and, after Layer 1
completes, **re-reads the real `policy_id` from Layer 1's own JSON
output** before invoking chunking/embedding/precompute — never assumes
`file_id` equals the canonical `policy_id`. That cross-check is exactly
what was missing when 954/955 were chunked manually earlier: nothing
forced the numeric filename convention and Layer 1's actual extracted
value (their real `policy_id` is the LIC UIN) to be compared.

## Built: check_concern_tags_sync.py + a documented checklist for changing the tag vocabulary

Raised directly by the user after walking through what changing a
concern_tag would actually require: the 8-tag vocabulary is duplicated
by necessity across `docs/prompts/prompt_b.txt` (what Gemini may
assign), `query/concern_tags.py` (the live-path canonical set),
`chunking/precomputed_rerank_scores.json`'s tag keys, and already-
extracted Layer 2 data — the same "manual, easy-to-forget re-sync
across files" shape as the 954/955 `policy_id` bug.

Considered building a full refresh script (auto re-derive Layer 2 +
re-run precompute), but explicitly declined by the user given today's
6-policy precompute run alone took ~2 hours at Voyage's free-tier pace
— an automatic trigger on every tag edit wasn't worth that cost.
Landed on: document the checklist directly in `docs/schema.md` next to
the Group A tag list (not buried in a progress log), plus a **read-only
check**, not an auto-fixer:

- `check_concern_tags_sync.py` (repo root): compares
  `query/concern_tags.py`'s tag set against `prompt_b.txt`'s declared
  list, `precomputed_rerank_scores.json`'s tag keys, and every
  `extracted/layer2_*.json`'s actually-assigned tags (flagging any tag
  used in already-extracted data that's no longer in the canonical
  set). Entirely local file reads/regex/JSON parsing — no Gemini or
  Voyage calls, so it's free to run anytime, not just after a tag
  change. Verified both the positive case (current 8-tag state reports
  in sync) and the negative case (a simulated fake tag-set mismatch, via

  running it for free after every new-policy ingestion too catches a
  freshly-derived Layer 2 assigning an out-of-vocabulary tag right when
  it's easiest to trace back to that specific ingestion run — a hard
  failure, not a warning, matching the script's existing verification
  steps (renumbered its echo'd step labels 1/4→1/5 etc. accordingly).
- `docs/schema.md`'s Group A section, `docs/ingestion_architecture.md`,
