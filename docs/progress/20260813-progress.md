## Standalone frontend deployed and verified

User imported `n8n/insurance_rag_frontend_webhook.json` into n8n and activated
it, then enabled GitHub Pages for the repo (both manual, outward-facing steps
deliberately left to the user rather than done automatically - see
2026-08-11's handoff). First load rendered the page correctly (CSS/layout
fine, confirming GitHub Pages itself was serving right) but every reply came
back as a blank chat bubble, not an error.

**Diagnosed from the blank-not-red distinction**: a red error bubble would
mean the `fetch` call itself failed (network/CORS); a blank bubble with no
error means the request succeeded but the response body didn't have the
shape `index.html` expected. Root cause: the Respond to Webhook node's
`respondWith: "allIncomingItems"` setting wraps the response in a JSON
array, so `index.html`'s `data.reply` read as `undefined` - which renders as
an empty string via `textContent`, not the literal word "undefined" (the
DOM's `textContent` setter treats `undefined` like `null`, coercing to `""`)
- explains exactly why it looked blank rather than showing an error or a
recognizable bad value.

**Fixed**: changed the node's "Respond With" option from "All Incoming
Items" to "First Incoming Item" directly in n8n's UI (`respondWith:
"firstIncomingItem"`) - took effect immediately on the already-active
workflow, no re-import needed. Fixed the same field in the repo's copy of
the workflow JSON so a future re-import starts correct.

**Full conversation verified after the fix**: age 31, cover ₹1Cr, concern
"replacing income for my family", term 30 (correctly rejected - "We don't
have premium data for a 30-year term matching your age/cover/concerns.
Available terms: 20, 25" - the live term-validation working exactly as
designed), term 25, payment option "regular" (correctly rejected too -
"Available options for this term: limited_ppt_10, limited_ppt_15,
limited_ppt_5, single"), "limited ppt 10", budget ₹20,000 - produced a real,
grounded recommendation (LIC's Yuva Credit Life / 877, ~₹14,305/yr, correct
pros/cons, correct disclaimer) with the candidates list rendering below the
narrative. Confirms the whole chain end-to-end: GitHub Pages -> CORS ->
n8n Webhook -> HTTP Request -> `/chat` -> eligibility/interpolation/
narrative generation -> Respond to Webhook -> back to the page.

The production webhook URL guessed on 2026-08-11

## Session 2: real user complaint traced to two genuine bugs, both fixed

User tried the new frontend for a realistic profile (age 31, ₹1Cr cover,
30-year term, regular premium) and got back only 1 candidate, with the
system rejecting term=30 and rejecting "regular" premium at term=25 as
unsupported - pushed back that this didn't seem right for such a standard
case. Investigated rather than reassuring - found two real, confirmed bugs,
not just a data-thinness limitation:

**Bug 1: `premium_lookup.json` silently never engaged for 954/955.**
`build_premium_lookup.py` keyed the built artifact by each policy's short
config label (`"954"`, `"955"`), but `interpolate_premium()` looks an entry
up by `layer1_record["policy_id"]` - the real extracted policy_id, which for
these two is a LIC UIN (`512N351V02`/`512N350V02`), not the short label. The
dict lookup missed every time, silently falling through to the old sparse
two-point linear interpolation - the exact same "filename id != real
policy_id" trap already flagged once before in this project (`ingest_policy.sh`'s
re-read-the-real-policy_id fix), just resurfacing in a different script.
Confirmed directly: age 31/term 30/regular on 954 returned "excluded: no
sample-premium table for term=30" despite `premium_lookup.json` genuinely
having that data.

**Bug 2 (compounding, related): the chat's live term/payment-option
validation checked the wrong data source.** `available_terms()`/
`available_payment_options_for_term()` in `premium_interpolation.py` only
ever scanned Layer 1's sparse `sample_illustrative_premiums` table (usually
one term per policy), never `premium_lookup.json`'s real, much wider grids
- true even for policies whose key matched correctly (876/875, both with
real regular-premium data out to term=40). This is what actually rejected
the user's term=30 and "regular" answers in the live chat.

**Fixes**:
1. `build_premium_lookup.py`: `main()` now reads each policy's own canonical
   `policy_id` from its `layer1_path` JSON (`_canonical_policy_id()`) and
   keys the output artifact by that instead of the config's short label.
   `DERIVED_POLICIES`' `derive_age_term_from` (still written using the short
   label, for readability) resolves through a small id map built during the
   same pass, so 955's derivation-from-954 still finds its source correctly.
2. `premium_interpolation.py`: rewrote `available_terms()` and
   `available_payment_options_for_term()` to route every candidate (term,
   payment_option) pair through `interpolate_premium()` itself - the real
   step-5 dispatch, including the precomputed lookup - instead of
   re-scanning the sample table in a second, independent path. One source
   of truth for "is this available" now, not two that can silently
   disagree (which is exactly what had happened).

**Verified, not just assumed fixed**:
- `interpolate_premium()` now returns a real bilinear estimate for 954 at
  (age 31, term 30, regular): ₹13,563.60, `method`
  `bilinear_age_30_35_term_30_x_percent_of_tabular_premium_x1.78`.
- `available_terms()`/`available_payment_options_for_term()` for the same
  profile now correctly include term 30 and "regular" at term 30 (previously
  excluded both).
- Full end-to-end simulation of the user's exact scenario (age 31, ₹1Cr,
  term 30, regular, budget ₹20,000, income_replacement) now returns **3 real
  candidates** instead of 1: 876 (₹11,508), 954 (₹13,563.60), 875
  (₹14,481.60) - 955 correctly excluded as over budget (₹23,207.63), 877
  correctly excluded as having no data at this exact combination (both
  exclusions logged, not silently dropped).
- Rebuilt `premium_lookup.json`, re-ran `validate_premium_lookup.py` for
  every built policy (876/859/875/878/954) - identical median/mean/max
  error numbers to before the fix, confirming no regression, just the key
  now resolving correctly. `premium_interpolation.py`'s hand-check suite and
  `check_concern_tags_sync.py` both still clean.
