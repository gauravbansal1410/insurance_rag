## Bug 1: Registration Number mistaken for Plan Number

954 and 955 both extracted `policy_id: "512"` with no low-confidence
flag. "512" is LIC's constant IRDAI corporate Registration Number,
printed identically on every LIC document's opening page ("Registration
Number: 512") — not a Plan Number. It also happens to match the numeric
UIN prefix on many LIC plans (e.g. `512N351V02`), which likely made it
look plausible to the model as a fallback identifier.

Root cause: neither document's Schedule has its "Plan Number" field
filled in for these two policies (both are blank template fields), and
no plan number appears anywhere else in either document's text — so
there was no correct value to extract in the first place, and the
existing trap 14 fallback (use UIN, flag `low_confidence_fields`) wasn't
followed.

Fix: added trap 15 to `docs/prompts/prompt_a_pdf.txt` and a matching
caveat to `docs/schema.md`, explicitly naming the Registration Number
pattern and directing the fallback to UIN + flag instead.

## Bug 2: prompt's own example value used as an anchor

After the trap 15 fix, re-running 954 still produced a wrong
`policy_id` — but a *different* wrong value: `"859"`, with no
low-confidence flag. 859 is Saral Jeevan Bima's real Plan Number from a
completely different policy — it doesn't appear anywhere in 954's source
documents. Reproduced twice, not a one-off.

Root cause: trap 14's own instructional text used a real corpus value as
its example — `(e.g. "859" for Saral Jeevan Bima)`. When the model
found no real Plan Number on 954 (same root cause as Bug 1: blank
Schedule field, no other mention), it appears to have echoed the
example value from its own instructions rather than following the
UIN-fallback rule.

Fix: reworded trap 14 in `docs/prompts/prompt_a_pdf.txt` to drop the
concrete "859" example and explicitly instruct the model not to reuse
any Plan Number value seen in the instructions or other documents.
Verified stable across 3 repeated runs on 954 after the fix (correct
UIN fallback, properly flagged both times). New trap 15 wasn't directly
re-exercised by this fix (that specific failure mode didn't recur), but
the UIN-fallback path it depends on is now confirmed working.

General lesson: a prompt's own example values are a real leakage risk
when the model can't find genuine source data to extract — worth a
second look on any prompt trap that embeds a real, specific value from
the corpus as illustration, versus reasoning from principle.
