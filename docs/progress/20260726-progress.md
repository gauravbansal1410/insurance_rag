## Bug 1: Registration Number mistaken for Plan Number

954 and 955 both extracted `policy_id: "512"` with no low-confidence
flag. "512" is LIC's constant IRDAI corporate Registration Number,
printed identically on every LIC document's opening page ("Registration
Number: 512") — not a Plan Number. It also happens to match the numeric
UIN prefix on many LIC plans (e.g. `512N351V02`), which likely made it
look plausible to the model as a fallback identifier.

Root cause: neither document's Schedule has its "Plan Number" field
filled in for these two policies (both are blank template fields), and
no plan number appears anywhere else in either document's text — so
there was no correct value to extract in the first place, and the
existing trap 14 fallback (use UIN, flag `low_confidence_fields`) wasn't
followed.

Fix: added trap 15 to `docs/prompts/prompt_a_pdf.txt` and a matching
caveat to `docs/schema.md`, explicitly naming the Registration Number
pattern and directing the fallback to UIN + flag instead.

## Bug 2: prompt's own example value used as an anchor

After the trap 15 fix, re-running 954 still produced a wrong
`policy_id` — but a *different* wrong value: `"859"`, with no
low-confidence flag. 859 is Saral Jeevan Bima's real Plan Number from a
completely different policy — it doesn't appear anywhere in 954's source
documents. Reproduced twice, not a one-off.

Root cause: trap 14's own instructional text used a real corpus value as
its example — `(e.g. "859" for Saral Jeevan Bima)`. When the model
found no real Plan Number on 954 (same root cause as Bug 1: blank
Schedule field, no other mention), it appears to have echoed the
example value from its own instructions rather than following the
UIN-fallback rule.

Fix: reworded trap 14 in `docs/prompts/prompt_a_pdf.txt` to drop the
concrete "859" example and explicitly instruct the model not to reuse
any Plan Number value seen in the instructions or other documents.
Verified stable across 3 repeated runs on 954 after the fix (correct
UIN fallback, properly flagged both times). New trap 15 wasn't directly
re-exercised by this fix (that specific failure mode didn't recur), but
the UIN-fallback path it depends on is now confirmed working.

General lesson: a prompt's own example values are a real leakage risk
when the model can't find genuine source data to extract — worth a
second look on any prompt trap that embeds a real, specific value from
the corpus as illustration, versus reasoning from principle.

## Layer 3 chunking — built and validated for term assurance (7/7)

Started from a chunking script drafted by Claude web AI
(`chunk_policy_doc.py`): structure-aware split of `policy_doc` text into
PART/Annexure sections via regex, using indentation to distinguish real
headers (indent ≥15, centered) from false-positive matches inside wrapped
body text (e.g. "...as per Part C of this Policy Document.", indent
4-8). The script's own docstring noted it had only been checked against
2 of the 7 term-assurance policies — validated it against all 7 before
trusting it.

Validation results: identical 9-chunk structure across every document
(`PART_A/B/C/D/F/G` + `ANNEXURE_1/2/3`), `PART_E` correctly dropped every
time (matches the existing `maturity_benefit: none` finding from
2026-07-12), ~99% content coverage, and the false-positive indent filter
confirmed doing real work — 4 of the 7 documents (875, 876, 877, 878)
actually contain the wrapped "Part C of this Policy Document" pattern,
and all were correctly excluded.

Two real bugs found and fixed during validation:
1. Cover-page boilerplate before the first header (LIC's corporate name,
   UIN, "Registration Number: 512") was being silently dropped —
   invisible in `dropped_sections`, unlike every other exclusion. Made
   it a pseudo-section (`PREAMBLE`) so it's logged like the rest — but
   this initially caused a second bug: at 33 words it cleared the
   `MIN_WORDS=10` threshold and would have been kept as a real,
   embeddable chunk. Fixed by making `PREAMBLE` an unconditional drop
   regardless of word count, since it's boilerplate identical across
   every LIC document and already captured in Layer 1's `plan_name`/`uin`.
2. `pdf_to_text()` was writing intermediate `.txt` files as siblings of
   the source PDF — i.e. directly into `raw_pdfs/`, which the README
   explicitly marks "do not modify manually." Switched to a
   `tempfile.TemporaryDirectory()` so nothing leaks into that directory.

**Caveat found, not a bug:** `section_name` (e.g. `PART_C`) is derived
purely from header position/letter, not content-verified — it assumes
the letter-to-meaning mapping (e.g. `PART_C` = Benefits) holds across
documents. Confirmed true across all 7 term-assurance policies, but only
checked within this one category. `section_title`, pulled from the
document's actual header text, stays correct even if that mapping ever
shifts. Documented in `docs/schema.md` under a new "Layer 3 — chunking
caveats" section, since it isn't a bug to fix but a reliability
assumption to re-check before trusting `section_name` semantically in a
future category.

Output: `chunking/chunk_policy_doc.py` + `chunking/chunks_<policy_id>.json`
for all 7 term-assurance policies, each with a `chunks` array and a
`dropped_sections` audit trail.

## Embedding + Qdrant load — built and validated for term assurance (7/7)

Locked collection name `insurance_rag_layer3` — single collection shared
across all categories, filtered by `policy_id`/`category` at query time,
matching how Layer 2's Group C fields already work (one schema, not
separate collections per category).

Built `chunking/embed_and_load_layer3.py`: embeds each chunk's
`chunk_text` via Voyage `voyage-law-2` (confirmed still valid, 1024-dim
output) and upserts into Qdrant, with the rest of the chunk's fields
(minus `chunk_text` itself, which is also kept in the payload for
narrative-generation grounding) as the point payload. Point IDs are a
`uuid5` derived deterministically from `chunk_id`, so re-running the
script on the same chunk always upserts the same point rather than
duplicating it.

**Rate-limit finding:** a Voyage account with no payment method on file
is capped at 3 RPM / 10K TPM. A naive single request embedding all 18
chunks (859+877 test set, ~24K estimated tokens) hit `RateLimitError`
immediately. A first fix — batching into <=5000-word groups spaced 21s
apart — still failed on the second batch: TPM turned out to be a
rolling 60-second window, not something that resets per request, so
batch 1's tokens hadn't cleared the window yet when batch 2 fired. Fixed
by spacing batches a full 65s apart, plus a retry-with-backoff fallback
as a safety net. Deliberately didn't ask for a payment method to be
added just to clear these free-tier caps — batching/pacing keeps this
at $0, matching the project's cost constraint, at the expense of wall-clock
time (the 63-chunk full run took ~16 batches, each ~65s apart).

**Test run (859, 877):** 18 chunks loaded → 18 embedded → 18 upserted →
collection reported 18 points total. Exact match, no silent partial
loss.

**Full run (all 7 term-assurance policies):** 63 chunks loaded → 63
embedded → 63 upserted → collection reported 63 points total. Exact
match again. `insurance_rag_layer3` now holds all term-assurance Layer 3
data.
