## query_architecture.md: steps 3-5 rewritten from design to implementation-ready

Design work happened in a separate claude.ai Project planning session;
this session translated it into concrete doc changes and code.

- **Step 3 (eligibility filter):** dropped the original "Qdrant payload
  filter" design in favor of an in-memory Python filter over Layer 2
  JSON loaded from `/extracted/`. No vector-search need exists for
  structured field filtering at this corpus's scale (32 policies max
  across all categories once fully extracted) — Qdrant stays scoped to
  Layer 3 narrative-chunk search only. Concern-tag matching (Group A)
  is now a hard gate (≥1 overlap required to pass), not just a sort
  input as originally designed. Riders are checked independently of
  their base plan — passing eligibility is never inherited.
- **Step 4 (fallback):** rewritten as an explicit two-tier relaxation.
  Tier 1 (<3 matches): relax Group C bounds only, concern gate stays
  firm. Tier 2 (still <3): also drop the concern gate. Budget is not
  relaxed at either tier, still step 5's job.
- **Step 5 (premium estimation):** replaced Gemini-based interpolation
  with deterministic two-point linear interpolation over Layer 1's
  `sample_illustrative_premiums`, matched within a single
  `premium_payment_option` column, scaled linearly for the profile's
  actual sum_assured against the table's baseline. Removed "whether
  Gemini can reliably interpolate premiums" from open questions (moot).
- Added a runtime-data-source note: the live query pipeline (n8n,
  Oracle VM) reads Layer 1/2 JSON from a local git clone kept current
  via manual end-of-session `git pull`, never a per-query GitHub raw
  fetch. Added the corresponding checklist item + credential-helper
  note to `docs/infra-baseline.md`.
- Added a new open question: Voyage's free-tier 3 RPM / 10K TPM cap
  (steps 6-7) is the real constraint on concurrent live-query
  throughput, not VM compute.

## Built and tested: query/ — steps 3-5 implementation

New `query/` directory, no test suite (matches project convention) —
each module's `__main__` block runs hand-checked profiles against real
`/extracted/` term-assurance data instead.

- `load_extracted.py`: loads all `/extracted/layer1_*.json` and
  `layer2_*.json` into memory, keyed by `policy_id` read from each
  file's JSON content — not parsed from the filename, since two files
  carry historical non-canonical names
  (`layer1_859_flashlite_pdf_v2_run1.json`,
  `layer1_877_flashlite_pdf_v3_run1.json`) from earlier test runs.
- `eligibility_filter.py`: `filter_eligible()` does the Group C bound
  checks (null-safe on `max_sum_assured` for the "No Limit, subject to
  underwriting" case) plus the concern-tag gate; `apply_fallback()`
  wraps it with the two-tier relaxation. Verified against real data:
  a realistic profile (age 30, SA 50L, term 20, income_replacement)
  clears tier 0 cleanly against 4 policies; dropping SA to 10L forces
  tier 1, since most term plans in this corpus have a 50L minimum
  (only 859 goes as low as 5L); an out-of-range age (5) also forces
  tier 1; a concern tag no term policy carries (retirement_income)
  correctly falls through to tier 2 with `concern_match_count: 0`
  across all 7.
- `premium_interpolation.py`: `interpolate_premium()` does the
  two-point interpolation + SA scaling; `filter_by_budget()` applies
  it to eligibility survivors and excludes-and-logs anyone over budget
  or outside a policy's sample-table range. Verified against 877's
  clean `limited_ppt_15`/term-25 column: exact-age match, true
  age-interpolation (midpoint of two real table values), and SA
  scaling all matched hand-calculated values from the raw table.

## Data-quality finding: ambiguous sample-premium rows on 4/7 term policies

While hand-verifying `interpolate_premium()`, found that 4 of the 7
term-assurance Layer 1 files (875, 876, 954, 955) contain exact
duplicate rows in `sample_illustrative_premiums` — identical on every
currently-extracted field (age, term, `premium_payment_option`,
`payment_mode`, `distribution_channel`, `sum_assured`) but with two
different `premium_amount` values. E.g. policy 875's age-30/term-20/
regular row exists twice: once at 5950, once at 8250. Nothing in the
current schema distinguishes them.

Root cause not confirmed, but the most likely explanation is an
uncaptured schema dimension — gender-split premium tables are common in
LIC brochures, and neither `docs/schema.md`'s
`sample_illustrative_premiums` field list nor the extraction prompt
models gender anywhere. (Notably, the query pipeline's own profile
collection in step 1 already asks for "smoker status" but not gender —
worth checking whether that's the actual differentiator instead, once
this is investigated properly.)

Rather than silently pick one of the two values — which would produce
a wrong premium quote for a real user — `interpolate_premium()` now
detects this case (`_ambiguous_ages()`) and hard-excludes with a
flagged reason, verified via `layer1["875"]`'s age-30/term-20/regular
combo. 877 and 878 have no such duplicates and were used for the clean
interpolation/scaling test cases instead.

**Not fixed today** — this needs a proper look at the source PDFs to
identify what the second dimension actually is, then a Layer 1 schema
+ prompt update and re-extraction. Flagged here so it isn't lost.
